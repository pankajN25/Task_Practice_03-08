PART 1 - THE BIG IDEA (explain this to them first)
===============================================================================

One app. Two tasks. Two interns.

At the top of the app there are 2 tabs:

     +---------------------------+  +--------------------------+
     | Task 1 - Feedback Form    |  | Task 2 - GitHub Search   |
     +---------------------------+  +--------------------------+
       ^ Intern A's work             ^ Intern B's work

Intern A clicks Tab 1 and sees his work.
Intern B clicks Tab 2 and sees her work.

Each intern has their OWN FOLDER. They never open each other's folder.

     src/task1/   <-- Intern A owns this folder. Only he edits it.
     src/task2/   <-- Intern B owns this folder. Only she edits it.

WHY THIS MATTERS (this is the important part):
Git merges code file by file. If two people edit the SAME file, git gets
confused and you get a "merge conflict" which is painful to fix.
Because Intern A only touches files inside src/task1/ and Intern B only
touches files inside src/task2/, they NEVER touch the same file.
So both their Pull Requests merge cleanly. Zero conflicts. Guaranteed.

The only way they can break this is by editing the shared files
(src/App.js or src/App.css). That is why those files say "DO NOT EDIT"
at the top.

FILE: src/App.js          (LOCKED - nobody edits this)
-------------------------------------------------------------------------------

WHAT IT DOES:
This is the switch board. It shows the 2 tab buttons at the top. When you
click "Task 1" it shows Intern A's work. When you click "Task 2" it shows
Intern B's work.

THE CODE INSIDE, EXPLAINED LINE BY LINE:

  import { useState } from 'react';
      -> useState is how React remembers something. Here it remembers
         which tab is currently open.

  import Task1App from './task1/Task1App';
  import Task2App from './task2/Task2App';
      -> Pulls in Intern A's work and Intern B's work.

  const [activeTask, setActiveTask] = useState('task1');
      -> "activeTask" holds either 'task1' or 'task2'.
      -> It starts as 'task1', so Task 1 is open when the app loads.
      -> "setActiveTask" is the function used to change it.

  <button onClick={() => setActiveTask('task1')}>
      -> Clicking the Task 1 button sets activeTask to 'task1'.

  className={activeTask === 'task1' ? 'tab active' : 'tab'}
      -> If this tab is the open one, give it the "active" style
         (white highlighted). Otherwise plain grey.

  {activeTask === 'task1' ? <Task1App /> : <Task2App />}
      -> THE KEY LINE. If activeTask is 'task1', show Intern A's component.
         Otherwise show Intern B's component. Only one shows at a time.

WHY IT IS LOCKED:
If both interns edit this file, git will hit a merge conflict. It is already
finished and wired up, so there is no reason for them to open it.

PART 3 - TASK 1 EXPLAINED (INTERN A)
===============================================================================

TASK NAME : Student Feedback Form
BRANCH    : task-1-feedback-form
FOLDER    : src/task1/
TIME      : roughly 4 to 6 hours

WHAT HE IS BUILDING, IN PLAIN WORDS:
A form where a student fills in feedback about a course. When he clicks
Submit, the app checks the form is filled correctly. If something is wrong,
red error text appears under that field. If everything is fine, the feedback
gets added to a list of cards below the form, and the form clears itself so
the next person can fill it. Each card has a Delete button.

WHAT IT SHOULD LOOK LIKE WHEN FINISHED:

  +-----------------------------------------+
  |  Full Name  [ Rahul Sharma          ]   |
  |  Email      [ rahul@                ]   |
  |             Email is not valid  <- red  |
  |  Course     [ React            v    ]   |
  |  Rating     [ 4                v    ]   |
  |  Comments   [ Very good course      ]   |
  |             18 / 200 characters         |
  |             [   Submit   ]              |
  +-----------------------------------------+

  Total feedback: 2

  +-----------------------------------------+
  |  Rahul Sharma          [ Delete ]       |
  |  rahul@gmail.com  |  React              |
  |  * * * * -                              |
  |  "Very good course"                     |
  +-----------------------------------------+
  +-----------------------------------------+
  |  Priya Singh           [ Delete ]       |
  |  priya@gmail.com  |  Node               |
  |  * * * * *                              |
  +-----------------------------------------+

THE 5 FORM FIELDS AND THEIR RULES:

  Field      | Input type | Rule
  -----------|------------|------------------------------------------
  Full Name  | text box   | Must be filled. At least 3 letters.
  Email      | text box   | Must be filled. Must have @ and a dot.
  Course     | dropdown   | Must pick one: React, Node, or Python.
  Rating     | dropdown   | Must pick a number from 1 to 5.
  Comments   | big box    | Optional. Max 200 letters. Show a live
             |            | counter like "18 / 200".

THE 7 THINGS THAT MUST WORK:

  1. Every input is "controlled". This is a React concept - it means React
     holds the typed value in memory, not the browser. He should keep all
     5 values in ONE useState object, like:
         const [form, setForm] = useState({ name:'', email:'', ... })

  2. Click Submit -> check all rules. If any rule fails, show red text
     directly under THAT field, and do NOT add anything to the list.

  3. If all rules pass -> add the entry to the list AND empty the form.

  4. Show the submitted entries below the form as cards, each showing:
     name, email, course, rating drawn as stars, and the comment.

  5. Every card has a Delete button that removes ONLY that one card.

  6. If the list is empty, show the text "No feedback submitted yet."

  7. Show a live count above the list: "Total feedback: 3"

HOW HE SHOULD SPLIT THE CODE (minimum 3 components):

  Task1App.js       <- holds the list of feedback in state (the "brain")
    |
    |-- FeedbackForm.js    <- the form and all the validation checks
    |
    |-- FeedbackList.js    <- loops over the entries
          |
          |-- FeedbackCard.js   <- draws ONE card + its Delete button

  Data flows DOWN through props. The Delete button sends a message back UP
  by calling a function that Task1App passed down to it.

BONUS (only if he finishes early):
  - Save the list in localStorage so it survives a page refresh.
  - Filter buttons: All / React / Node / Python.

PART 4 - TASK 2 EXPLAINED (INTERN B)
===============================================================================

TASK NAME : GitHub User Search Dashboard
BRANCH    : task-2-user-search
FOLDER    : src/task2/
TIME      : roughly 5 to 8 hours

WHAT SHE IS BUILDING, IN PLAIN WORDS:
A search box where you type a GitHub username. The app then goes to the
internet, fetches that person's GitHub profile, and displays their photo,
name, follower count, and their top 5 most-starred repositories.

The real lesson here is handling the 3 situations that happen with any
internet request:
   - It is still loading      -> show "Loading..."
   - It failed                -> show an error message
   - It worked                -> show the data

Most beginners only handle the third one. That is the point of this task.

THE 2 WEB ADDRESSES SHE USES (free, no password needed):
   https://api.github.com/users/octocat
   https://api.github.com/users/octocat/repos?per_page=100

She can paste those in a browser to see the raw data she will be working with.

WHAT IT SHOULD LOOK LIKE WHEN FINISHED:

  +--------------------------------------------------+
  |  [ octocat                    ]  [  Search  ]    |
  +--------------------------------------------------+

  +--------------------------------------------------+
  |  (photo)   The Octocat                           |
  |            @octocat                              |
  |            A short bio line here                 |
  |                                                  |
  |   Followers 9821 | Following 9 | Repos 8         |
  |            [ View on GitHub ]                    |
  +--------------------------------------------------+

  Top repositories        Sort by: [ Stars ] [ Name ]

  +--------------------------------------------------+
  |  Hello-World          * 2453      JavaScript     |
  |  My first repository on GitHub                   |
  +--------------------------------------------------+
  |  Spoon-Knife          * 1204      HTML           |
  |  This repo is for demonstration purposes         |
  +--------------------------------------------------+

THE RULES THAT MUST WORK:

  SEARCH BOX
  1. A text box plus a Search button.
  2. Pressing the Enter key must also start the search.
  3. If the box is empty, show "Please enter a username" and do NOT
     contact the internet at all.

  THE 3 STATES (this is what is really being tested)
  4. WHILE LOADING  -> show "Loading..." and grey out the Search button
                       so it cannot be clicked twice.
  5. IF USER NOT FOUND (error code 404) -> show "User not found"
  6. IF ANY OTHER FAILURE -> show "Something went wrong. Try again."
  7. IF IT WORKED -> show the profile card.

  PROFILE CARD
  8. Show the photo, real name, @username, and bio.
  9. Show 3 numbers: Followers, Following, Public repos.
  10. A "View on GitHub" link that opens in a NEW browser tab.

  REPOSITORY LIST
  11. Fetch her repos and show only the TOP 5 with the most stars.
  12. Each row shows: repo name (clickable link), description,
      star count, and programming language.
  13. If the user has zero repos, show
      "This user has no public repositories."
  14. A toggle to re-sort the list: by Stars, or by Name A-Z.

  ONE MORE IMPORTANT RULE
  15. When a NEW search starts, the old user's data and any old error
      message must disappear immediately. A very common beginner bug is
      leaving the previous person's photo on screen while loading the
      next one.

HOW SHE SHOULD SPLIT THE CODE (minimum 3 components):

  Task2App.js       <- holds user, repos, loading, error in state
    |
    |-- SearchBar.js   <- the input box and Search button
    |-- UserCard.js    <- the profile card
    |-- RepoList.js    <- the repo rows and the sort toggle

TEST USERNAMES SHE SHOULD TRY:
   octocat        -> normal user, has repos
   torvalds       -> famous user, many repos
   asdkjhaskdjh12 -> does not exist, should show "User not found"

BONUS (only if she finishes early):
  - Debounce: search automatically 500ms after she stops typing.
  - "Recent searches" list of the last 5 names, clickable to search again.


===============================================================================
PART 5 - THE RULES BOTH INTERNS MUST FOLLOW
===============================================================================

MUST DO:
  1. Make your own branch before writing any code:
        Intern A:  git checkout -b task-1-feedback-form
        Intern B:  git checkout -b task-2-user-search
  2. Only edit files inside YOUR OWN folder.
  3. Commit in small steps with clear messages. Not one giant commit
     at the end saying "done".
  4. Push your branch, then open a Pull Request into master.
     Do NOT merge it yourself - wait for review.
  5. In the PR description write: what you built, what is not finished,
     and how long it took.
  6. "npm start" must run with NO red errors and NO yellow warnings
     in the browser console (press F12 to see the console).

MUST NOT DO:
  1. Do not edit src/App.js or src/App.css - these are locked shared files.
  2. Do not open or edit the other person's folder.
  3. Do not install any new packages. No axios, no bootstrap, no MUI,
     no react-router. Plain React and plain CSS only.
     (Reason: the point is to learn React itself, not a library.)
  4. Do not use class components. Function components with hooks only.
  5. Do not use the array position number as a "key" in a list.
     (Reason: it causes wrong-item bugs when you delete something.)
  6. Do not change state directly. This is WRONG:  list.push(newItem)
     This is RIGHT:  setList([...list, newItem])


===============================================================================
PART 6 - HOW YOU REVIEW THEIR WORK
===============================================================================

When their Pull Request arrives, check these 5 areas:

  1. DOES IT ACTUALLY WORK?
     Pull their branch, run npm start, and click through every requirement
     in their folder's README.md checklist.

  2. STATE HANDLING
     - Are all inputs controlled?
     - Did they copy arrays instead of push-ing into them?
     - Is state in the right (parent) component?

  3. COMPONENT SPLIT
     - Did they create at least 3 components, or dump everything into
       one giant file?
     - Is data passed down through props properly?

  4. THE EDGE CASES (this separates a good intern from an average one)
     - Task 1: empty list message, validation errors, delete correctness
     - Task 2: loading state, 404 error, no-repos message, stale data

  5. GIT HABITS
     - Several small clear commits, or one messy commit?
     - Is the PR description filled in?
     - Did they stay inside their own folder? (check the "Files changed"
       tab - if you see App.js there, they broke rule 1)
